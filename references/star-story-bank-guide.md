# STAR 故事库构建

## 从账本到故事

1. 每个账本条目（E{NN}）按「可讲的故事角度」拆出候选故事——一个条目可出多个故事，一个故事只锚定一个主冲突。
2. 故事骨架：S/T 合并 ≤2 句 → A＝第一人称具体动作（决策点+取舍）→ R＝账本量化点（带来源标注）。
3. **R 准入线**：没有像样 R 的故事不进库——回追问清单要数据，或换角度。「学到了很多」不是 R。

## 故事 × 题型映射表

```markdown
| 故事 | 来源条目 | T2 项目深挖 | T3-冲突 | T3-失败 | T3-压力 | T3-团队 | 备注 |
|---|---|---|---|---|---|---|---|
| 支付模块重设计 | E04 | ◎ 主用 | | | ○ 可用 | | 90s 版+3min 版各备 |
| 跨部门数据打通 | E02 | ○ | ◎ 主用 | | | ○ | 冲突落点在推进机制 |
```

- ◎ 主用 / ○ 备用；一场面试同一故事只讲一次——映射表就是防重复调度表。
- 覆盖检查：T2/T3 四子类每格至少一个 ○，缺格＝库不完整，回账本再挖。

## 故事卡（交付格式）

用 `assets/story-card-template.md`。每卡含：一句话版（钩子）/ 90 秒版（默认应答）/ 3 分钟版（深挖展开）/ 追问预案（该故事最可能被追的 2-3 个点及答法）。

## 失败故事特别规则

- 必须是真失败（有代价：损失/返工/被否），假失败（「我太追求完美」）在 QA 中按卖点错配级处理。
- 结构：失败事实 → 当时的错误判断 → 代价 → 之后**做法层面**的改变（不是态度层面）→（如有）后续验证。
- 失败故事的 R＝改变后的可验证行为差异。
